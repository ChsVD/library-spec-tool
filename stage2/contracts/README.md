# 阶段二内建操作规约表

这里保存经独立审核发布的公共规约，供不同待证明库复用。初始索引为空。运行阶段二时使用默认目录即可，隔离实验可用 `--contract-store <目录>`。

## 文件与版本

`index.json` 记录各操作在给定编译配置下的当前版本与正文摘要。标准接口正文位于 `stdlib/<头文件>/<条目>/<配置摘要>/v1.json` 等文件中。Clang 扩展使用 `extensions/clang/<条目>`。源码名称、调用方库名和模型生成的标签都不作为识别操作的证据。第一版支持阶段一已确认的 Clang 内建调用。识别普通标准库函数还需要可靠的声明来源。

配置由工具从阶段一的 Clang 版本、翻译单元编译参数、目标平台和记录的编译器默认 C 模式提取。工具对相同配置复用规则；缺少足够配置、涉及无法解析的参数或同一定义出现多种配置时，查询返回 `configuration_unknown`。规则正文只应描述有依据的语义。版本由发布工具分配。团队共享时应一起提交索引和新增版本文件。

## 三个工具如何配合

1. 写作代理对当前任务的内建调用执行 `lookup_contract`。多个 ID 可放在同一查询中，共用规则正文只返回一次。
2. 缺少语义或现有规则确有错误时，写作代理调用 `propose_contract_change`。新建时 `base_version` 为 0。调用代码违反了有效规约时，直接记录调用点的问题。无法建立可靠依据时，可以保留未知。
3. 独立审核代理检查标准条款、配置、触发代码与前后正文，通过 `review_contract_change` 批准或退回。只有批准才会发布新版本。并发修改了同一基础版本时，过期提案会标为 `stale`。写作代理得到理由后重新查询、修订。每次写作审核轮最多进行两次提案往返，之后使用已批准条目或保留缺口。
4. 函数审核代理收到固定版本的正文和具体调用位置，检查该函数是否满足条件。运行日志与函数检查点保存在运行输出目录；读取已批准规则无需再次审批。

## 提案格式示例

下面展示两个调用共用规则正文时的写法。调用 ID 取自当次任务。此示例仅用于说明工具参数。实际条目由审核代理确认具体条件和适用范围后生成。

```json
{
  "tool": "propose_contract_change",
  "call_ids": ["<初始化调用 ID>", "<结束调用 ID>"],
  "base_version": 0,
  "reason": "两处调用使用同一个局部 va_list，需要核对其生命周期。",
  "spec": {
    "id": "stdlib/stdarg/va_list_lifecycle",
    "source": "WG14 N1570 §7.16.1、§7.16.1.3、§7.16.1.4",
    "operations": {
      "__builtin_va_start": {"name": "va_start", "requires": "满足该语言模式对变参函数、末个具名参数和列表的约束。", "ensures": "初始化给定的变参列表。"},
      "__builtin_va_end": {"name": "va_end", "requires": "存在对应的初始化，且尚未结束该次使用。", "ensures": "结束这次对变参列表的使用。"}
    },
    "checks": ["沿相关返回路径核对同一列表的初始化与结束，包括提前返回。"]
  }
}
```

调用审核将结论附在各自的 `call_id` 上。阶段二输出的 `contract-changes.json` 可查看新增和修改的条目、旧版与候选正文、审核决定及理由。[WG14 N1570 第 7.16 节](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)
