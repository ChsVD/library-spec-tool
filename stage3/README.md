## 阶段二选择结果如何传入（2026-10-30）

stage2.select 和人工请求的 stage2.demand_scope 都输出 scope-plan.json、SCOPE.md 和范围图。自动选择还输出 selection.json、assessment.json，供用户检查选择理由和静态预算。

先审核函数组与边界，再向本阶段传入 --scope-plan 和 --approve-scope 对应的 plan_digest。不要将选择运行目录直接当作已经生成规约的目录，也不要因为选择器报告 within_limits 就跳过本阶段的输入预算检查。选择结果不构成已证明契约。

阶段二选择说明

> **适用范围**：本阶段面向一个待证明库和若干个已证明参考库。下文 OpenSSL BN、SM2、mini-GMP 及相关路径是当前案例；参考库数量不限定为两个。通用设计与当前实现限制见 [开发指南](../DEVELOPMENT.md)。

> **目录已按四阶段调整（2026-10-30）**：stage1 为模块分析，stage2 为函数图与范围选择，stage3 为自然语言规约，stage4 为通用定义和引理。阶段四使用 --stage3-run 指定自然规约目录，--stage2-run 仍作为兼容别名。历史运行内容不修改。完整流程见 [开发指南](../DEVELOPMENT.md)。

> 顺序纠正：自然规约生成默认 caller-first，自顶向下逐层传递需求；底层优先仅用于后续证明规划。此前 callee-first 生成实验已作废。使用 --continue-from 配合 --regenerate 可只沿用目标范围，重新生成全部规约与需求。

# 阶段三：生成自然语言推荐规约

当前目标是提供可阅读的参考草稿，不保证正确性、完备性或强度。直接输入模块说明和函数实现，不要求完整源码提取包或 callee 已证明规约。草稿生成后默认进行独立模型审核及有限修订；这不是形式化证明。默认命令 `python -m stage3` 已切换到新实现。

## 多目标函数组入口

现在可以从已保存的模块图规划一批目标函数的需求子图并集，再开始自然规约生成。读取图、按确切函数 ID 选组、向下展开目标的被调用依赖并补齐 SCC，再向上汇总需求路径、保留边界背景，详见 函数组需求范围。该入口不重复构图，范围规划不运行模型；执行时通过 --scope-plan 和 --approve-scope 绑定已审核计划。原有按整个 manifest 处理的入口仍兼容。

## 工作流程

1. 从模块或函数组清单枚举函数，保留源码位置和配置背景。模块说明沿用阶段一材料。
2. 程序建立调用关系。图中调用边从调用者指向被调用者；无法解析的调用、宏和条件实现保留为未知，不阻止生成参考规约。
3. 将相互递归的函数合并为强连通分量（SCC），得到分量之间无环的依赖图。默认按调用者分量在前的顺序起草；继续既有运行时仍可使用已生成调用者提出的需求。可通过 --order caller-first 显式指定此顺序。这些需求不是已证明保证。
4. 每个分量启动独立模型会话，提供模块说明、当前完整实现、一跳关系和已经生成的邻居草稿。分量过大时拆批，但保留分量成员身份；同一分量后生成的草稿可以看到先生成的假设，不进行固定点迭代或一致性证明。
5. 输出每个函数的源码观察、推荐规约、假设与未知、对 callee 的需求。先验证 JSON、目标覆盖和必要文本，再由独立会话审核语义、前提、精确输出和资源条件；程序不执行形式化检查。
6. 每批立即保存。格式错误最多修复一次；模型连接失败、过大上下文留下记录，可断点续跑，不丢弃其他草稿。

## 输入和命令

输入仍使用已有 manifest，其 materials 中有 `target-module` 时只传目标模块说明，否则使用指定材料。原始源码按索引记录的字节位置读取完整函数；索引缺口保留原有清单发现及未知标记。函数实现直接提供，不复制类型/宏的完整依赖闭包。配置与类型不明时由模型写出假设。

先在 WSL 项目根目录执行 bash scripts/setup_graph.sh 配置依赖。

只生成依赖图与分量计划，不调用模型：

```sh
python3 -m stage3 --manifest stage2/manifests/openssl-bn-module.json --output runs/reference-plan --prepare-only
```

使用现有 Codex 登录生成草稿：

```sh
python3 -m stage3 --manifest stage2/manifests/openssl-bn-module.json --output runs/reference-specs --model gpt-6.1-sol --reasoning-effort high --context-chars 60000
```

小批实验可以增加 `--max-components 2`；这限制本次处理的分量数，不修改整个模块的目标集合。相同命令增加 `--resume` 会继续尚未完成的函数。每次模型调用默认超时 600 秒，可用 `--call-timeout` 修改。

## 输出

- `graph.json`：函数实现、调用边、未知关系、强连通分量、处理顺序、推荐规约与下层需求。
- `specs/<id>.md` 和 `.json`：逐函数推荐规约。
- `tasks/`：每批输入、模型原始输出、格式修复和失败记录。
- `identity.json`：输入快照、材料和模型配置；输入变化后拒绝沿用旧结果续跑。
- `SUMMARY.md`、`status.json`：草稿生成进度，不是证明进度。

当前默认复用固定版本 FM-Agent 的 C 后端：CodeGraph 建立函数索引，Clang JSON AST 建立直接调用边，未覆盖函数回退到 CodeGraph，并加入函数指针值流/类型匹配候选。详见 依赖图与环境配置。旧词法图仅通过 --graph-backend lexical 显式选择。SCC 只针对当前识别出的候选图，未知关系不会伪装成没有依赖。单个函数、模块说明或邻居上下文太大时保存输入并标记 context_too_large，不静默截断源码。

## 旧流程

旧入口移至 `python -m stage2.legacy_cli`，旧说明见 README_LEGACY.md，仅用于历史实验复现。源码提取仍为独立步骤；默认使用新的轻量独立审核，可选 --with-common 衔接公共候选生成；已有人工修改文件与实验结果保留。当前不生成 QCP/Coq 规约、通用 lemma、strategy 或证明。

## 不设应用层上下文预算的测试

增加 `--no-context-limit` 可关闭输入、输出及格式修复过程的字符预算检查，也不再按字符预算拆分 SCC。不能与 `--context-chars` 同时使用。此模式在 identity.json 中记录 max_chars=null；不会设置模型输出 token 上限，但模型/服务自身限制仍然适用。调用超时、一次格式修复、落盘和续跑机制保持有效。

## 向下继续与精简输出（2026-10-20）

`--continue-from <旧运行目录>` 与模块级 manifest 配合，先建立完整模块候选图，再保留旧运行目标及其可达下层函数。验证旧输入快照与函数身份，继承已有参考草稿、沿新边传递旧调用者需求，不重写旧结果。新结果写入单独目录。默认 `--order caller-first`；同一 SCC 内不人为声称存在严格先后顺序。无法解析的宏/外部调用仍列为未知，当前可达闭包不等于完整的实际调用闭包。

2026-10-27 起，生成提示采用“职责与符号 + 命名规约的 With / Require（Pre）/ Ensure（Post）”，详见 [自然规约模板](NATURAL_SPEC_TEMPLATE.md)。内存、边界及失败行为统一写入前后条件，不再单列 Modifies / Fail；假设和未知仍单列。原地与分离等场景可分别命名，每份有完整前后条件；同一契约的结果分支可在 Ensure 中表达。允许存在量和析取，但要求结果明确、资源正确、覆盖范围不被缩小。对确定性计算，Ensure 还须明确由入口输入得到的计算结果及其数学含义，并连接返回值和输出内存；要求后续形式化接口直接暴露计算结果或提供已证明等价的接口。暂用唯一关系时必须标明待补充的计算接口与等价连接，不能将结果唯一视为接口已经完善。这些是生成要求，程序尚未增加语义检查。既有草稿保留原样；续跑只对新生成部分应用新提示，统一格式需在新目录中使用 --continue-from 配合 --regenerate。

```sh
python3 -m stage3 --manifest stage2/manifests/openssl-bn-module.json --continue-from runs/reference-bn-word-sol61-high-unlimited-20261020-01 --output runs/new-downstream --no-context-limit --order caller-first
```

## 多分支汇总同一底层函数（旧辅助入口）

新的多目标流程使用 demand_scope；下面的单目标辅助函数保留兼容，不作为新版默认范围规划器。

`stage2.branch_scope.select` 根据完整模块图，保留指定入口到目标函数的所有已识别路径；另外加入尚未覆盖的直接调用者。路径外兄弟依赖仍记为未知，同名但没有目标路径的平台版本单独记录，不伪造调用边。按 caller-first 为各分支逐层生成需求，目标函数最后接收全部已识别直接调用者的草稿、需求和原始调用点窗口。

重复调用点分别保留。调用者失败时，尚未执行的下层标记 upstream_incomplete；恢复后重试。若旧执行中已经产生缺少上层需求的下层草稿，必须使该调用者的可达下层结果失效并重生成，不能只重试失败入口后沿用旧目标稿。

bn_add_words 多分支试验在各链完成后增加一次 Sol 汇总，比较各调用点的长度、原地覆盖、重叠、进位使用和配置假设，形成统一参考规约及逐分支需求说明。汇总会核对直接调用者是否逐项覆盖，但仍不构成语义或强度验证。


## 衔接阶段四（2026-10-27）

默认入口支持 --with-common，可选 --common-output 指定公共候选目录。只有本次范围全部生成草稿后才启动阶段四；--prepare-only 不启动，部分完成时保留结果并返回失败。阶段四也可独立读取现有参考稿：

    python3 -m stage4 --stage3-run runs/reference-specs --output runs/common-candidates

新版 status.json 记录 workflow、graph_digest 和 expected_function_ids，供下游核对交接范围。阶段四继承假设、未知项和实际审核状态；审核通过仍未证明，显式跳过审核的稿件仍标为未审核。此次连接只生成并审查公共候选，尚不产出 Coq 文件。预算、恢复和旧结果兼容规则见 [阶段四说明](../stage4/README.md)。


## 独立审核与有限修订（2026-10-27）

默认流程为：每批起草 → 新会话独立审核 → 必要时修订 → 新会话复核。审核通过后才将需求传给下一层。每个审核会话只收到模块说明、原始函数实现、调用关系/已有邻居稿及本批候选，不共享生成会话历史。不要求先完成源码提取、callee 证明或全库分析。

八项检查分别是输入域、精确输出、入口快照、内存资源、分支覆盖、调用需求、假设与未知、可计算结果接口。审核必须逐项给出结论与依据；pass 不允许同时含未解决项或阻断问题。需要修订和材料不足必须有具体问题及修正方向。程序检查报告结构及结论一致性，语义判断由模型完成，不保证正确性。

- 默认 --max-revisions 1：最多一次语义修订，之后重新独立审核。设为 0 时只审核。
- 格式错误最多修复一次；模型连接异常不自动重复调用。
- needs_revision 超出修订次数后保存 review_needs_revision；insufficient 保存 review_insufficient，不在缺材料时盲目修订；调用/格式失败保存 review_failed 或 revision_failed。
- 未通过的批次保留最新草稿，阻止下层生成，并禁止作为已完成范围交接阶段四。
- --skip-review 显式保留旧的只生成参考稿方式；此时不声称经过审核。

审核和修订使用与生成相同的单次超时、字符预算；不截断过长材料。SCC 仍按原规则拆批，审核只覆盖本批及给定上下文，不增加跨批固定点检查，也不声称递归正确性已证明。一个批次只有全部通过才放行。

每次尝试保存于 tasks/<批次>/attempt-N/，包括初稿、审核输入输出、修订稿、复核和失败原因。节点及 specs/<id>.json 保存审核报告与规约/源码摘要，Markdown 展示当前审核状态。独立审核前先保存 pending_review 草稿，中断后可继续审核；已通过的结果不重复调用。重试使用新目录，不覆盖前次记录。每次显式恢复仍受本次有限修订次数约束。

输入快照、模型、审核策略或提示变化时拒绝沿用原审核运行身份；草稿变化不能沿用旧审核。上层审核失效时，已识别可达下层的审核也失效，重新按新需求核对。旧未审核运行可继续使用 --skip-review 恢复；若要启用新版审核，使用新输出目录和 --continue-from，继承草稿后重新审核，或加 --regenerate 全部重生成。

全部通过时总体状态为 reviewed_reference_drafts，semantic_review=true、proved=false。阶段四校验审核报告、草稿和源码摘要；候选审查不会将其升级为已证明。新审核使用模拟模型离线测试，尚未启动真实模型或证明实验。


## 生成前情景分析与领域关注点（2026-10-28）

默认生成流程新增“先分析情景，再书写规约”。同一负责生成的 agent 在同一次结构化响应中，先输出每个函数的 scenario_analysis，再输出 suggested_spec。修订时也使用相同要求；不额外启动情景分析模型会话，不把分析自述当作语义审核结果。既有独立审核及 --skip-review 行为保持不变。

可维护文件为 [DOMAIN_CONCERNS.json](DOMAIN_CONCERNS.json)：general_requirements 是所有函数需考虑的通用要求；domains 同时包含领域目录（id/title/when_relevant）及各领域 points。可直接增补领域和关注点，不需改 Python。id 用稳定英文标识，说明用中文；general/custom 为保留领域名。领域可组合，目录外情景可在输出中用 custom.<名称> 补充，不因函数属于某个库就强制纳入该领域的全部性质。

内置目录包含整数与数组、链式结构、数值计算、状态机、并发、输入输出、编码解析和密码接口。它是可扩展的起始目录，不表示领域覆盖完整。尤其不能预定零长使用哪种 QCP 写法，也不能将“存在空数组引理”写成当前环境调用匹配已通过。

每份情景分析包含情景概括、领域选择及理由、关注项的具体依据与规约影响、适用/不适用/未知状态和材料缺口。通用要求逐项考虑；所选领域至少引用一个实际相关关注点，不要求抄写所有领域条目。程序只检查字段、目录 ID、覆盖和引用结构，不检查分析是否真实正确，不能将其称为验证基准。

可用 --domain-catalog /path/to/catalog.json 指定另一份同结构目录。运行开始时加载一次，并保存 writing-guidance.json；identity.json 记录内容摘要，即使 --skip-review 也检查。目录变化会拒绝在原运行中恢复，避免新旧生成要求混用；如要继续原目录版本，可显式指定该运行保存的 writing-guidance.json。旧版本无此身份字段的运行不自动迁移，保留原结果，新生成使用新输出目录。

情景分析保存在每份 spec JSON 的 scenario_analysis、Markdown 的“生成前情景分析（生成者自述，未验证）”，以及任务目录的 generated-scenarios.json/final-scenarios.json。审核后的修订分析和初稿分析分别保留。仅 --prepare-only 会保存目录并规划任务，不生成分析或规约。目录计入上下文预算，过大时明确报告而不截断。
